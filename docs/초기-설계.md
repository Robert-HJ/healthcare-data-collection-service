# 초기 설계

## 설계 전제와 범위

제공된 자료만으로는 모바일 앱과 각 건강 플랫폼의 실제 연동 방식, `recordkey`의 발급 주체를 확인할 수 없다. 구현에 필요한 범위를 정하기 위해 다음과 같이 전제한다.

- Samsung Health와 Apple HealthKit 입력은 출처는 다르지만 `recordkey`, `source`, `entries`를 포함하는 공통 구조를 사용한다. 모바일 앱 또는 별도의 수집 계층이 각 플랫폼의 데이터를 읽어 공통 전송 형식으로 만든 뒤 백엔드에 전달한다고 본다.
- 회원가입 시 계정과 1:1로 연결되는 `recordkey`가 생성된다고 본다. `recordkey`는 활동 한 건이 아니라 건강 데이터의 소유자를 나타내며, 데이터베이스 내부의 회원 기본키와는 구분한다.
- `entries`는 개별 실시간 이벤트가 아니라 이미 종료된 시간 구간의 활동 집계값으로 해석한다.
- `from`과 `to`가 같은 순간 엔트리는 별도의 의미를 지닌 데이터가 아니라 다른 엔트리들과 동일한 성격의 데이터로 전제한다.
- 백엔드는 플랫폼 권한 요청이나 기기 내부 데이터 조회를 담당하지 않는다. 공통 형식의 입력을 받은 이후 사용자 인증, 데이터 소유 관계 확인, 정규화, 적재, 집계와 조회를 담당한다.

## 전체 흐름

1. 사용자가 회원가입하면 계정과 1:1로 연결되는 `recordkey`가 생성된다.
2. 로그인을 하게 되면 서버에서 인증 토큰(JWT)을 반환한다.
3. 동기화 API는 JWT를 포함해 호출하며 서버는 이를 검증하고 인증 사용자와 `recordkey`의 관계, `source`, 요청의 기본 구조를 확인한다.
4. 전달받은 원본 입력과 Outbox 이벤트를 데이터베이스에 함께 저장한 뒤 `202 Accepted`를 응답한다.
5. Outbox 이벤트를 Kafka로 발행한다.
6. Kafka 메시지를 받은 처리기는 저장된 원본 입력을 읽어 출처별 차이를 정규화한다.
7. 정규화된 데이터를 활동 원장에 저장하고, 영향을 받는 일별·월별 집계를 갱신한다.
8. 조회 API는 `recordkey`를 기준으로 일별·월별 집계 데이터를 조회한다. (`source`별 분리 조회는 확장 범위)

HTTP 요청은 동기화 작업의 완료까지 기다리지 않는다. 따라서 모바일 앱이 처리 결과를 확인할 방법은 필요하지만, 이를 위한 식별값과 API 형식은 비동기 동기화 기능을 구현할 때 결정한다.

## 주요 의사결정과 판단 근거

### `recordkey`를 회원과 연결한다

회원가입 정보에는 `recordkey`가 없고 활동 데이터에는 회원을 구분할 다른 값이 없다. 앞서 정한 전제에 따라 회원가입 시 계정과 연결되는 값을 생성하고, 로그인 사용자는 자신의 `recordkey`에 속한 데이터만 저장하고 조회할 수 있게 한다.

### 동기화 요청과 실제 적재를 분리한다

한 번의 입력에 다수의 활동 구간이 포함되고, 신규 설치나 장기간 미동기화 후에는 요청 크기가 더 커질 수 있다. 사용자 수가 늘어나면 여러 동기화 요청이 같은 시간대에 몰릴 수도 있다.

모든 레코드의 변환, 저장, 집계를 HTTP 요청 안에서 수행하면 큰 요청 하나가 응답 시간을 길게 만들고 서버의 요청 처리 자원을 오래 점유한다. 동기화 API는 요청을 유실 없이 접수하는 역할까지만 수행하고 실제 적재는 Kafka를 통해 비동기로 처리한다.

### 데이터베이스 저장과 Kafka 발행 사이의 유실을 막는다

동기화 요청을 데이터베이스에 저장한 뒤 Kafka에 바로 발행하면, 두 작업 중 하나만 성공하는 경우가 생길 수 있다. 요청은 접수됐지만 메시지가 발행되지 않거나, 데이터베이스 기록 없이 메시지만 전달되는 상황을 피해야 한다.

동기화 요청과 Outbox 이벤트를 하나의 데이터베이스 트랜잭션으로 저장한 뒤, Outbox 이벤트를 Kafka로 발행한다.

### 원본 수신 데이터와 활동 원장을 분리한다

Samsung Health와 HealthKit은 시각과 수치 표현 방식이 다르다. 이러한 차이를 정규화 단계에서 해소해 두면 이후의 적재, 집계와 조회 로직은 데이터 출처마다 분기하지 않고 일관된 형태를 사용할 수 있다.

다만 정규화 과정에서 잘못된 변환이 발생할 수 있으므로 모바일 앱에서 받은 원본 입력은 변경하지 않고 별도로 보관한다. 정규화된 데이터는 이후 비즈니스 로직이 사용하는 활동 원장으로 관리하고, 원본 입력은 변환 결과를 검증하거나 데이터를 다시 처리할 때 사용한다.

### 활동 원장과 집계 데이터를 함께 유지한다

일별·월별 조회 때마다 누적된 활동 원장을 `GROUP BY`하면 데이터가 늘어날수록 조회 비용이 커진다. 반대로 집계 결과만 저장하면 처리 오류를 검증하거나 집계를 다시 만들 원장 데이터가 사라진다.

정규화된 활동 원장을 기준 데이터로 보고, 자주 조회하는 일별·월별 결과는 별도 집계로 유지한다. 원장 변경과 집계 변경은 같은 데이터베이스 트랜잭션에서 완료해 서로 다른 상태가 되는 것을 막는다.

## 단계별 설계

### 1. 회원가입과 접근 제어

회원가입 시 이름, 닉네임, 이메일, 비밀번호를 입력받고 계정과 연결되는 고유한 `recordkey`를 생성한다. 이때 `recordkey`가 계정과 1:1로 연결된다는 것은 확정된 사실이 아니라 구현 범위를 정하기 위한 전제다. 비밀번호는 평문으로 저장하지 않고 BCrypt 단방향 해시로 보관한다. 이메일과 비밀번호로 로그인한 뒤 동기화와 조회 기능을 사용할 수 있다.

로그인 유지는 JWT access 토큰으로 처리하고, 재발급을 위한 refresh 토큰은 회전(rotation)과 폐기를 위해 MySQL에 저장한다. 서버는 클라이언트가 전달한 `recordkey`를 그대로 신뢰하지 않고 로그인한 계정의 값과 일치하는지 확인한다.

### 2. 동기화 요청 접수

동기화 API는 실제 적재를 시작하기 전에 다음 내용만 확인한다.

- 로그인한 사용자가 자신의 `recordkey`로 요청했는지
- 지원하는 `source`인지
- 이후 처리를 시작할 수 있는 기본 입력 구조인지

개별 활동 레코드의 상세 검증과 변환은 비동기 처리 단계에서 수행한다. 접수 단계에서 모든 레코드를 순회하면 요청 처리와 실제 적재를 분리한 효과가 줄어들기 때문이다.

`202 Accepted`를 응답하기 전에는 전달받은 원본 입력이 다시 읽을 수 있는 상태로 저장돼 있어야 한다. 원본 입력은 정규화 과정에서 변경하지 않으며, Outbox 이벤트에는 해당 입력을 찾기 위한 참조만 기록한다.

### 3. Kafka 전달

Outbox 발행 처리는 아직 발행되지 않은 이벤트를 Kafka에 전달한다. 같은 회원과 출처의 동기화 순서를 유지할 수 있도록 메시지 키에는 입력에 포함된 `recordkey`와 `source`를 사용한다. 서로 다른 회원의 데이터는 여러 처리기가 병렬로 처리할 수 있다.

Outbox 발행과 Kafka 소비 과정에서는 같은 이벤트가 다시 전달될 수 있다. 메시지를 반드시 한 번만 전달한다고 가정하지 않고, 다음 저장 단계가 반복 실행돼도 최종 결과가 같도록 만든다.

### 4. 정규화와 활동 원장 적재

처리기는 Kafka 메시지를 통해 접수된 원본 입력을 찾고, `source`에 맞게 각 `entries`를 공통 활동 형태로 변환한다. 정규화된 데이터는 활동 원장에 저장되며, 활동 원장은 이후 집계와 조회에서 사용하는 기준 데이터다. 정규화 결과에 문제가 발견되면 보관된 원본 입력과 활동 원장을 비교할 수 있다.

시각 표현은 출처마다 기준이 다르다. Samsung Health의 `from`/`to`는 오프셋이 없는 로컬 벽시각이고, Apple HealthKit의 `from`/`to`는 UTC(+0000)다. 원장에는 이를 하나의 절대 시각(UTC 인스턴트)으로 통일해 저장하고, 이후 집계 경계는 이 값을 기준으로 계산한다. 수치도 출처마다 표현이 다르다. Apple의 `steps`는 문자열이며 소수 값을 포함하므로, 원장에는 소수 정밀도를 보존해 파싱·저장하고 정수 표현이 필요한 조회 응답에서 반올림한다. Apple의 `calories`가 0으로 들어오는 값은 그대로 보존한다.

같은 회원의 같은 `source` 안에서 `from`과 `to`가 모두 같은 데이터는 동일한 활동 구간으로 본다. 다시 전달되면 새로운 행을 추가하지 않고 기존 측정값을 갱신한다. `from`이나 `to` 중 하나라도 다르면 별개의 구간으로 저장한다.

제공 데이터에는 `from`은 같지만 `to`가 다른 구간이 실제로 있으므로 `from`만으로 동일한 활동을 판단하지 않는다. 데이터베이스에도 회원, `source`, `from`, `to` 조합에 유일성 제약을 두어 요청 재전송이나 Kafka 재전달이 중복 적재로 이어지지 않게 한다.

Samsung Health에는 `from`과 `to`가 같으면서 측정값이 존재하는 엔트리가 포함돼 있다. 현재 입력만으로 해당 엔트리가 별도의 의미를 가지는지 확인할 수 없으므로, 앞에서 정한 설계 전제에 따라 다른 활동 엔트리와 동일하게 취급한다. `from == to`라는 이유로 제거하지 않고 별도의 활동 원장 데이터로 저장하며, `from`이 속한 일자의 집계에 포함한다. 위 유일성 제약 `(회원, source, from, to)`가 이 경우도 그대로 적용된다.

### 5. 일별·월별 집계

활동 원장이 변경되면 그 구간이 속한 일자와 월의 집계를 갱신한다. 원장 적재와 집계 반영은 하나의 데이터베이스 트랜잭션 안에서 처리한다.

집계의 일·월 경계는 원장의 UTC 저장값과 분리된 결정이다. UTC 자정으로 자르면 사용자가 기대하는 하루와 어긋날 수 있으므로, 집계 경계는 서비스 기준 타임존(현재 `Asia/Seoul`)으로 변환한 날짜를 기준으로 자른다. 어떤 타임존으로 집계했는지는 집계 데이터에 함께 기록하며, 숫자 오프셋 대신 DST·타지역 확장을 흡수할 수 있는 IANA 존 ID(`Asia/Seoul`) 형태로 저장한다. 또한 사용자가 서로 다른 기기(`source`)를 사용해 데이터를 전달할 수도 있으므로 타임존 값과 같이 `source` 값을 집계 유일성 키에 포함한다. 즉 집계 키는 `(recordkey, 기간[일자 또는 월], source, timezone)`으로 구성한다. 현재는 서비스 타임존이 사실상 단일 값이고 제공 데이터에서 `source` 값도 중복되지 않으므로 조회 시 이 키들로 분기하지는 않으며, 이후 확장 범위로 둔다.

동기화 요청의 활동 데이터를 원장에 모두 반영한 뒤 실제로 변경된 일자를 중복 없이 수집해 원장 변경 이벤트를 발행한다. 커밋 이전에 실행되는 트랜잭션 이벤트 리스너(`@TransactionalEventListener(phase = BEFORE_COMMIT)`)는 변경된 일자의 활동 원장을 다시 합산해 일별 집계를 갱신하고, 갱신된 일별 집계를 기준으로 월별 집계를 다시 계산한다. 집계 처리에 실패하면 활동 원장 변경도 함께 롤백한다.

이때 일별·월별 집계 값은 소수 정밀도를 유지해 저장하고, 정수 반올림은 조회 응답에서만 수행한다. 월별 집계를 일별 집계에서 다시 계산할 때 반올림된 값을 합산해 오차가 누적되는 것을 막기 위함이다.

### 6. 일별·월별 조회

조회 API는 로그인 사용자의 `recordkey`를 받아 일별·월별 집계를 조회한다. 서버는 조회에서도 로그인 계정과 `recordkey`의 관계를 확인한다.

실제 집계 기준은 Source와 Timezone이 포함되어 있어 내부에서 기본 값으로 Asia/Seoul을 사용하고 source 값은 응답 포맷에 포함시키도록 한다.

### 7. 실패와 재처리

Outbox 발행이 실패하면 데이터베이스에 남은 이벤트를 다시 발행할 수 있어야 한다. Kafka 처리에 실패한 요청도 재처리할 수 있어야 하며, 반복 처리되더라도 활동 원장의 유일성 제약과 재집계 방식으로 중복 결과를 막는다.

비동기 처리의 진행 상태, 재시도 기준, 반복 실패한 요청의 보관 방식은 구현 전에 별도로 설계한다. 현재 단계에서는 API가 접수한 요청이 이후 단계의 일시적인 실패 때문에 사라지지 않아야 한다는 원칙만 정한다.

## 확장 범위

다음 항목은 현재 요구사항과 제공 데이터 범위 밖이므로 이번 구현에 포함하지 않고, 필요 시 확장한다.

- refresh 토큰 저장소의 Redis 이전(TTL 자동만료·빠른 조회).
- 일별·월별 조회 API 조건에 `source`, `timezone` 확장 고려.

## 현재 설계의 한계

현재 입력에는 플랫폼 활동의 고유 ID, 삭제 여부, 수정 버전이 없다. 따라서 `from` 또는 `to`가 달라진 데이터가 새로운 활동인지 기존 활동의 수정인지 구분할 수 없다. 현재는 별개의 활동으로 저장하며, 이후 플랫폼의 활동 ID와 수정·삭제 정보를 받을 수 있다면 이를 우선해 수정/삭제를 반영하는 구조로 확장한다.
