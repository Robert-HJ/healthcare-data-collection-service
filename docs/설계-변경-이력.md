# 설계 변경 이력

## 2026-07-30 데이터 유형별 처리와 저장 구조 구체화

초기에는 서로 다른 출처와 데이터 유형을 하나의 정규화 결과와 활동 원장으로 통합하는 구조를 고려했다. 하지만 현재 제공된 `steps` 데이터에 맞춰 걸음 수, 거리와 칼로리 칼럼을 고정한 상태에서 모든 건강 데이터 유형을 포괄하는 구조라고 설명하기는 어렵다. 건강 데이터는 유형마다 필요한 값과 집계 기준이 달라질 수 있고, 이름이 같은 측정값도 데이터 유형에 따라 의미와 범위가 다를 수 있다.

현재 구현은 제공된 데이터에 맞춰 `health_step_data`와 `health_step_daily_aggregation`으로 구체화한다. 데이터 유형이 테이블 자체에 드러나므로 두 테이블에서 항상 같은 값이 되는 `data_type` 칼럼은 제거한다. 수집 요청에는 원본 계약과 처리 대상 확인을 위해 `data_type`을 계속 저장한다.

비동기 Worker는 수집 요청의 `source`와 `data_type`에 맞는 처리기를 선택한다. 처리기는 해당 입력의 정규화, 전용 테이블 적재와 집계 갱신을 맡으며 서로 다른 데이터 유형의 정규화 결과를 하나의 공통 객체로 만들지 않는다. 현재는 `steps`만 구현하고, 구조가 다른 데이터 유형이 추가되면 해당 유형의 테이블과 처리기를 함께 추가한다. 두 처리기에서 실제로 동일한 저장 또는 집계 코드가 확인되면 그때 공통 기능을 분리한다.

## 2026-07-28 정규화 데이터 적재와 일별 집계 처리 기준 확정

수집 요청의 원본과 처리 상태를 저장한 뒤에는 입력의 각 활동 구간을 공통 형식으로 정규화해 별도 테이블에 적재한다. 한 행은 입력의 `entries` 한 건에 대응하며 내부 회원 식별값, 출처, 데이터 유형, UTC로 변환한 시작·종료 시각과 걸음 수·거리·칼로리를 가진다. 같은 데이터를 다시 처리했을 때 중복 행이 생기지 않도록 `(member_id, source, data_type, started_at, ended_at)` 조합을 유일성 기준으로 사용한다. 현재 값을 만든 원본 요청도 함께 기록해 정규화 결과를 원본과 비교할 수 있게 한다.

정규화된 시각은 집계 타임존에 종속되지 않는 UTC 값으로 유지한다. 일별 집계는 회원, 집계 타임존, 출처, 데이터 유형과 집계 일자를 기준으로 저장한다. 현재 서비스 집계 타임존은 `Asia/Seoul`이며 집계 결과에도 사용한 IANA 타임존을 기록한다. 월별 집계 테이블은 별도로 만들지 않고 조회 시 일별 집계 최대 31건을 합산한다.

입력의 활동 값은 `from`과 `to` 사이 구간 전체의 합계이고, 자정을 넘는 구간을 날짜별로 나눌 수 있는 세부 정보는 제공되지 않는다. 값을 양쪽 날짜에 모두 포함하면 중복 집계되고, 시간 비율로 나누면 활동이 균일했다는 근거 없는 가정이 들어간다. 따라서 구간 전체 값은 집계 타임존에서 `started_at`이 속한 날짜에 귀속한다. `from`과 `to`가 같은 데이터도 같은 기준으로 처리한다.

수집 Worker는 정규화 과정에서 이번 요청이 영향을 준 시작 시각을 확인하고, 원장을 upsert한 뒤 해당 날짜 범위의 정규화 데이터를 다시 조회해 일별 합계를 전부 계산한다. 이번 요청의 값만 기존 집계에 더하지 않는 이유는 같은 날짜의 기존 데이터와 동일 구간의 수정값까지 반영해야 하기 때문이다. 정규화 데이터 저장, 일별 집계 갱신과 요청 완료는 하나의 트랜잭션으로 처리하며, 현재는 이 사이에 내부 이벤트나 별도 집계 작업을 두지 않는다.

여러 Worker가 같은 요청을 가져가는 문제와 서로 다른 요청이 같은 집계를 동시에 변경하는 문제는 구분한다. 요청 행은 `FOR UPDATE SKIP LOCKED`로 선점하고, `(member_id, source, data_type)`이 같은 처리 그룹에서는 아직 끝나지 않은 요청 중 가장 작은 요청 ID만 선점할 수 있게 한다. 앞선 요청이 `PROCESSING`이거나 다시 처리할 수 있는 실패 상태라면 다음 요청은 기다린다. 서로 다른 처리 그룹은 병렬로 실행할 수 있다.

처리 순서를 위해 회원 행을 잠금 대상으로 사용하는 방안도 검토했지만, 수집 기능이 회원 정보 수정과 불필요하게 경합하고 잠금의 목적이 테이블의 역할과 맞지 않아 제외했다. Kafka에서 회원 키를 기준으로 순서를 보장하는 방안은 다중 인스턴스 작업 분배와 순서 보장에 유효하지만, 현재는 데이터베이스 작업 큐에서 같은 기준을 구현할 수 있다. 선점 쿼리와 상태 전이는 실제 MySQL에서 여러 Worker가 동시에 실행되는 테스트로 검증하고, 이 부분이 병목이 될 때 Kafka 도입을 다시 검토한다.

## 2026-07-27 동기화 비동기 처리와 집계 구조 변경

초기에는 동기화 API가 원본 요청과 Kafka 발행 대상을 함께 저장한 뒤, 메시지 처리기가 정규화부터 활동 원장 적재와 집계까지 수행하도록 계획했다. 요청 처리와 후속 작업을 분리해 빠르게 응답하고, 실패한 작업을 다시 처리하려는 판단이었다.

원본 보관, 출처별 정규화와 활동 원장 저장은 같은 서비스가 이어서 수행하는 하나의 수집 과정이다. 이 사이에 Kafka를 두고 원본 전체를 전달하면 큰 메시지를 다뤄야 한다. 원본의 식별값만 전달하면 후속 처리기가 다시 같은 데이터베이스에서 원본을 읽어야 하므로 실제 역할이 나뉘는 것도 아니다. 현재 필요한 비동기 실행과 실패 재처리는 MySQL의 처리 상태와 작업 조회로 해결할 수 있어 Kafka를 추가하지 않기로 했다.

동기화 API는 검증을 통과한 원본 요청과 처리 상태를 하나의 트랜잭션으로 저장한 뒤 `202 Accepted`로 응답한다. 커밋 이후 트랜잭션 이벤트 리스너는 별도 스레드에서 수집 작업을 바로 시작하도록 알리는 역할만 한다. 이 신호가 사라지거나 처리 중 장애가 발생해도 폴링 스케줄러가 데이터베이스의 처리 상태를 확인해 미처리 요청과 다시 처리할 수 있는 실패 요청을 실행한다. 따라서 요청을 잃지 않고 다시 처리할 수 있는 근거는 이벤트가 아니라 저장된 원본과 처리 상태다.

수집 작업은 원본 정규화, 활동 원장 저장, 영향받은 일자의 집계 갱신과 요청 처리 완료를 하나의 트랜잭션으로 처리한다. 집계는 기존 값에 차이를 더하지 않고 해당 일자의 활동 원장을 전부 다시 합산한다. 같은 요청이 반복되어도 원장을 기준으로 같은 결과를 만들 수 있고, 중간에 실패하면 원장과 집계 변경이 함께 롤백되어 저장된 원본에서 전체 작업을 다시 시작할 수 있다. 월별 결과는 조회할 때 일별 집계 최대 31건을 합산하며 별도 월별 집계 테이블은 만들지 않는다.

원장 저장과 집계를 별도 작업으로 나누면 수집 트랜잭션을 짧게 만들 수 있지만, 현재 규모에서는 집계 대상과 처리 상태를 관리하는 테이블, 별도 처리기와 재처리 흐름이 추가되는 비용이 더 크다고 판단했다. 우선 같은 회원의 동기화 작업이 동시에 처리되지 않도록 하고 원장과 일별 집계를 한 번에 처리한다. 이후 수집 트랜잭션이 길어지거나 같은 날짜의 집계 갱신에서 잠금 경합이 반복되고, 수집과 집계를 독립적으로 확장해야 하는 상황이 확인되면 원장 변경과 함께 재집계 대상을 저장하고 별도 집계 작업이 처리하는 구조로 분리한다.

현재는 Kafka와 Redis를 사용하지 않는다. 데이터베이스에서 처리 대상을 조회하고 여러 처리기가 작업을 나누는 과정이 실제 병목으로 확인되거나, 처리 기능을 별도로 확장해야 할 때 Kafka 도입을 검토한다. 외부 서비스가 활동 원장 변경 내용을 받아야 하는 경우에도 Kafka를 사용할 수 있다. 이때 외부 서비스가 우리 데이터베이스를 다시 조회하지 않도록 처리에 필요한 정규화 데이터를 메시지에 담고, 메시지가 지나치게 클 때만 별도 저장소에 데이터를 두고 위치를 전달한다.

운영 중에는 처리되지 않은 원본 요청의 수, 실패 및 재시도 횟수, 오랫동안 처리 중인 상태로 남은 요청을 지표와 로그로 확인한다. 폴링 스케줄러가 마지막으로 정상 실행된 시각도 상태 정보로 제공한다. 애플리케이션이 중단되어 스케줄러 자체가 실행되지 않는 상황은 외부 모니터링에서 감지하고 알리도록 구성한다.

## 2026-07-27 동기화 요청 검증 범위 확대

초기 설계에서는 동기화 API가 요청의 소유 관계와 최상위 구조만 확인하고, 개별 활동 데이터의 상세 검증은 비동기 처리 단계에서 수행하도록 계획했다. 접수 단계에서 활동 데이터를 순회하지 않아 HTTP 요청 처리 시간을 줄이려는 판단이었다.

제공 입력은 최대 약 1,500개의 활동 데이터를 포함하지만, 이를 한 번 순회해 형식을 확인하는 비용은 이후의 원장 적재와 집계 작업에 비해 크지 않다. 반면 형식이 잘못된 요청까지 `202 Accepted`로 접수하면 비동기 수집 작업이 다시 실행되어도 성공할 수 없고, 클라이언트는 입력 오류를 즉시 확인할 수 없다.

이에 따라 동기화 API가 모든 활동 데이터의 필수 구조와 타입, 출처별 시간 및 수치의 변환 가능 여부를 확인한 뒤 요청을 접수하도록 변경한다. 인증 사용자의 `recordkey` 소유 관계와 지원하는 활동 유형 및 출처도 이 단계에서 함께 확인한다. `from`과 `to`가 같은 데이터는 제공 입력에 실제로 존재하므로 정상으로 허용하고, `memo`처럼 처리에 영향을 주지 않는 추가 필드는 허용한다.

검증에 실패한 요청은 원본을 저장하지 않고 `400 Bad Request`로 응답한다. 검증을 통과한 요청만 원본과 처리 상태를 하나의 트랜잭션으로 저장한 뒤 `202 Accepted`로 응답한다. 비동기 수집 작업은 접수된 요청이 처리 가능한 형식이라는 전제에서 정규화, 원장 적재와 일별 집계 갱신을 수행하며, 재시도는 일시적인 인프라 장애와 같이 다시 처리했을 때 성공할 수 있는 오류를 대상으로 한다.

## 2026-07-25 Refresh Token 구현 제외

초기 설계에서는 로그인 시 Access Token과 Refresh Token을 발급하고, Refresh Token의 회전과 폐기를 위해 MySQL에 저장하는 구조를 계획했다. 구현 범위를 검토한 결과 현재는 Access Token만 발급하는 구조로 변경한다.

현재 요구사항은 이메일과 비밀번호를 이용한 로그인과 인증된 API 호출이며, Access Token만으로도 이를 충족할 수 있다. 반면 Refresh Token을 도입하려면 토큰 발급뿐 아니라 다중 기기 로그인, 재발급 시 회전, 로그아웃과 폐기, 탈취 토큰의 재사용 감지, 동시 재발급 요청과 만료 데이터 정리까지 함께 다뤄야 한다. 이 중 일부만 구현하면 로그인 유지 기능은 제공하더라도 안전한 세션 관리 구조라고 보기 어렵다.

현재 구조에서는 Access Token이 만료되면 사용자가 다시 로그인해야 하며, 발급된 토큰을 서버에서 즉시 폐기할 수 없다. 로그아웃은 클라이언트가 토큰을 제거하는 방식으로 처리한다. 이 제한을 줄이기 위해 Access Token의 만료 시간을 제한적으로 설정한다.

향후 로그인 유지가 필요해지면 단순 로그인 이력이 아니라 현재 유효한 인증 세션을 관리하는 별도 모델을 추가하고, Refresh Token의 회전과 폐기 정책을 함께 구현한다.
